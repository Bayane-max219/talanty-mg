1. Présentation du projet

TalantyMG est une marketplace (place de marché) en ligne permettant à des freelances malgaches (appelés PROVIDER) de proposer leurs services, et à des clients (appelés CLIENT) de les réserver.

Fonctionnalités principales

Côté CLIENT

  • Inscription / Connexion
  • Parcourir les services disponibles
  • Voir le détail d'un service
  • Réserver un service (avec message)
  • Suivre ses réservations

Côté PROVIDER (Freelance)

  • Inscription / Connexion
  • Créer et publier des services
  • Voir les réservations reçues
  • Confirmer ou refuser une réservation
  • Marquer une mission comme terminée

2. Architecture globale — 3 couches

🖥️ FRONTEND — Next.js 14 + TypeScript + Tailwind CSS
Interface utilisateur — Port 3000 — http://localhost:3000
↕ HTTP + JWT Bearer Token
🔀 MIDDLEWARE — Node.js + Express
Sécurité, validation, agrégation — Port 3001
↕ HTTP + JWT Spring Security
⚙️ BACKEND — Spring Boot 3 + JPA/Hibernate
Logique métier, base de données — Port 8080
↕ JDBC / SQL
🗄️ BASE DE DONNÉES — PostgreSQL 16
Stockage persistant — Port 5432
Pourquoi 3 couches ?
Cette architecture sépare les responsabilités : le frontend gère l'affichage, le middleware gère la sécurité et l'agrégation de données, le backend gère la persistance. Chaque couche peut être modifiée indépendamment.

Communication entre les couches

DeVersProtocoleSécurité
Frontend (3000)Middleware (3001)HTTP REST + JSONJWT Token (middlewareTalantyMG)
Middleware (3001)Backend (8080)HTTP REST + JSONJWT Token (Spring Security)
Backend (8080)PostgreSQL (5432)JDBC / SQLUser/Password + Réseau Docker interne
Sécurité Double JWT : Le frontend utilise un token signé par Node.js. Node.js utilise un autre token signé par Spring Boot. Ce sont deux secrets distincts. Même si quelqu'un intercepte le token frontend, il ne peut pas accéder directement à Spring Boot.

3. Docker Compose — Containerisation

Docker Compose permet de lancer les 4 services avec une seule commande : docker-compose up. Chaque service tourne dans son propre container isolé.

# docker-compose.yml — simplifié
services:
  postgres:         # Container 1 — Base de données
    image: postgres:16-alpine
    environment:
      POSTGRES_DB: talanty_db
      POSTGRES_USER: talanty_user
    ports: ["5432:5432"]
    volumes:
      - postgres_data:/var/lib/postgresql/data  # Données persistantes
    healthcheck:                                 # Vérifie que Postgres est prêt
      test: pg_isready -U talanty_user

  backend-api:      # Container 2 — Spring Boot
    build: ./backend-api
    ports: ["8080:8080"]
    depends_on:
      postgres:
        condition: service_healthy   # Attend que Postgres soit prêt

  middleware-api:   # Container 3 — Node.js
    build: ./middleware-api
    ports: ["3001:3001"]
    environment:
      SPRING_API_URL: http://backend-api:8080   # URL interne Docker
      RATE_LIMIT_WINDOW_MS: 60000               # Fenêtre rate limit = 1 min

  frontend:         # Container 4 — Next.js
    build: ./frontend
    ports: ["3000:3000"]
Le réseau interne Docker (talanty-net) permet aux containers de communiquer entre eux par leur nom (backend-api, postgres) sans exposer ces ports à Internet. Seuls les ports 3000, 3001, 8080 sont accessibles depuis votre machine.

4. Base de données — PostgreSQL

Tables créées automatiquement par Spring Boot (JPA/Hibernate)

Spring Boot crée les tables automatiquement au démarrage grâce à spring.jpa.hibernate.ddl-auto=update.

TableDescriptionColonnes principales
users Comptes utilisateurs id, full_name, email, password (BCrypt), role (CLIENT/PROVIDER/ADMIN), created_at
service_offers Services proposés par les freelances id, title, description (TEXT), category, price, image_url (TEXT), delivery_days, is_active, provider_id (FK→users)
bookings Réservations id, client_id (FK→users), service_id (FK→service_offers), status (PENDING/CONFIRMED/COMPLETED/CANCELLED), client_note, created_at
reviews Avis clients id, booking_id (FK), rating, comment, created_at

Relations entre tables

users ──(1→N)──→ service_offers   # Un PROVIDER a plusieurs services
users ──(1→N)──→ bookings          # Un CLIENT fait plusieurs réservations
service_offers ──(1→N)──→ bookings # Un service peut être réservé plusieurs fois
bookings ──(1→1)──→ reviews        # Une réservation terminée peut avoir un avis

5.1 Les modèles JPA (model/)

Chaque classe @Entity représente une table en base de données. Les annotations définissent les colonnes, les relations et les contraintes.

@Entity                                           // → crée la table "users"
@Table(name = "users")
@Getter @Setter @NoArgsConstructor @Builder       // → Lombok génère get/set/constructeurs
@JsonIgnoreProperties({"hibernateLazyInitializer", "handler"}) // → Fix Hibernate Proxy
public class User {

    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;                              // → auto-increment PRIMARY KEY

    @Email @NotBlank
    @Column(unique = true, nullable = false)
    private String email;

    @Enumerated(EnumType.STRING)
    @Column(nullable = false)
    private Role role = Role.CLIENT;

    @JsonIgnore                                   // → Évite la récursion infinie
    @OneToMany(mappedBy = "provider", cascade = CascadeType.ALL,
               fetch = FetchType.LAZY)
    private List<ServiceOffer> services;           // → Relation 1→N vers services
}
Problème Hibernate Lazy Loading résolu :
Quand Hibernate charge un objet en FetchType.LAZY, il crée un "proxy" (objet intermédiaire via ByteBuddy). Jackson ne sait pas sérialiser ce proxy en JSON. La solution : @JsonIgnoreProperties({"hibernateLazyInitializer", "handler"}) sur chaque entité (User, ServiceOffer, Booking).
Problème de récursion infinie résolu :
Sans protection : User → services → ServiceOffer.provider → User → … → StackOverflowError.
Solution : @JsonIgnore sur User.services pour briser le cycle.

5.2 Les repositories (repository/)

Les repositories héritent de JpaRepository. Spring Data JPA génère automatiquement les requêtes SQL à partir des noms de méthodes.

public interface ServiceOfferRepository extends JpaRepository<ServiceOffer, Long> {
    // Spring génère automatiquement : SELECT * FROM service_offers WHERE provider_id = ?
    List<ServiceOffer> findByProviderId(Long providerId);

    // Génère : SELECT * FROM service_offers WHERE is_active = true
    List<ServiceOffer> findByIsActiveTrue();
}

6. Middleware — Node.js Express

Le middleware est un serveur Node.js qui fait le lien entre le frontend et Spring Boot. Il joue le rôle de "gardien" : toutes les requêtes passent par lui.

6.1 Rôles du middleware

🔐 Sécurité

  • Valide le JWT du frontend
  • Rate limiting (anti-spam)
  • Helmet (sécurité HTTP)
  • CORS (origines autorisées)

✅ Validation

  • Vérifie les données entrantes
  • Format email, longueur password
  • Retourne des erreurs 400 claires

📊 Agrégation

  • Combine plusieurs APIs
  • Dashboard = 3 appels parallèles
  • Formate les données pour le frontend

6.2 Point d'entrée — app.js

const express = require('express');
const app = express();

// ── Sécurité HTTP ────────────────────────────────────────────────
app.use(helmet());                    // Ajoute des headers de sécurité HTTP
app.use(cors({ origin: 'http://localhost:3000' })); // Autorise seulement le frontend

// ── Rate Limiting ────────────────────────────────────────────────
const globalLimiter = rateLimit({
  windowMs: 60000,    // Fenêtre de 1 minute
  max: 500,           // Max 500 requêtes par minute
  message: { error: 'Trop de requêtes' }
});
app.use(globalLimiter);

// ── Routes ───────────────────────────────────────────────────────
app.use('/api/auth', authLimiter, authRoutes);
app.use('/api/services', serviceRoutes);
app.use('/api/bookings', bookingRoutes);
app.use('/api/dashboard', dashboardRoutes);

6.3 Middleware d'authentification JWT (middleware/auth.js)

const authenticate = (req, res, next) => {
  const token = req.headers.authorization?.replace('Bearer ', '');
  if (!token) return res.status(401).json({ error: 'Token manquant' });

  try {
    const decoded = jwt.verify(token, process.env.JWT_SECRET);
    req.user = decoded;    // Attache l'utilisateur à la requête
    next();                // Continue vers le controller
  } catch {
    res.status(401).json({ error: 'Token invalide' });
  }
};

// Vérification du rôle
const requireRole = (role) => (req, res, next) => {
  if (req.user.role !== role)
    return res.status(403).json({ error: 'Accès refusé' });
  next();
};

8. Flux complets — Exemples de bout en bout

8.1 Flux de connexion

// 1. Frontend → Middleware
POST http://localhost:3001/api/auth/login
Body: { email: "user@test.mg", password: "MonMotDePasse" }

// 2. Middleware → Spring Boot (avec validation)
POST http://backend-api:8080/api/v1/auth/login

// 3. Spring Boot → Vérifie BCrypt(password) == hash en BDD
// 4. Spring Boot → Génère JWT Spring → renvoie à Middleware
// 5. Middleware → Génère JWT Middleware → renvoie au Frontend
// 6. Frontend → Stocke dans localStorage → Redirige vers /dashboard

8.2 Flux de création de service

// 1. Frontend (PROVIDER) → Middleware
POST /api/services  +  Authorization: Bearer <jwt-middleware>
Body: { title, description, category, price, deliveryDays, imageUrl }

// 2. Middleware → Vérifie JWT → Vérifie rôle = PROVIDER
// 3. Middleware → Spring Boot
POST http://backend-api:8080/api/v1/services  +  Authorization: Bearer <jwt-spring>

// 4. Spring Boot ServiceOfferService.java :
offer.setIsActive(true);           // Force car @Builder ignore les valeurs par défaut
offer.setAverageRating(0.0);
offer.setProvider(currentUser);
serviceOfferRepository.save(offer); // → INSERT INTO service_offers ...

// 5. Retour JSON → Middleware → Frontend → Toast "Service créé !"

9. Problèmes techniques rencontrés et solutions

ProblèmeCauseSolution
StackOverflowError — "Infinite recursion" Jackson sérialisait User → services → ServiceOffer.provider → User → … @JsonIgnore sur User.services
ByteBuddyInterceptor — "Type definition error" Hibernate crée des proxy objects pour le Lazy Loading que Jackson ne sait pas sérialiser @JsonIgnoreProperties({"hibernateLazyInitializer","handler"}) sur chaque @Entity
429 Too Many Requests Fenêtre rate limit de 15 min dépassée lors des tests RATE_LIMIT_WINDOW_MS=60000 (1 minute)
isActive = null en base de données @Builder Lombok ignore les valeurs par défaut des champs Setter explicite : offer.setIsActive(true); dans le service layer
IMAGE trop longue → erreur 400 imageUrl VARCHAR(255) trop court pour base64 Colonne TEXT + compression canvas (400×300, JPEG 70%)
Docker CACHED — fix Java ignoré Docker utilise le cache de build même si le code change docker-compose build --no-cache backend-api
